Module 09

Agents & Tool Use

⏱ ~12 min read

What you'll learn

  • What tool use / function calling lets an LLM do.
  • What an "agent" is and how it chains steps.
  • The reliability and safety implications of letting AI take actions.

Tool use: giving the model hands

On its own, an LLM can only produce text. Tool use (also called function calling) changes that. The application gives the model a menu of functions it's allowed to request — a calculator, a web search, a database lookup, "create a ticket," "send an email." When the model decides a tool would help, it outputs a structured request; the application runs it and feeds the result back so the model can continue.

This is powerful because it fills the LLM's gaps. It's bad at arithmetic and frozen at its knowledge cutoff — but it can call a calculator and a live search to compensate. The model decides what to call; your code controls whether and how it actually runs.

IT analogy

Tool use is like giving a smart but sandboxed script a set of approved API calls. It can request an action, but it only gets the capabilities you expose — and you decide the permissions on each one.

From single answers to agents

An agent is what you get when you let the model loop: reason about a goal, choose an action or tool, observe the result, then decide the next step — repeating until the task is done. Instead of answering once, it plans and executes a sequence of steps.

For example, an IT agent asked to "diagnose why a user can't print" might: check the print queue (tool), read the device status (tool), search the knowledge base (tool), then summarize a fix. Each step's result informs the next. That chaining is what makes agents feel capable — and what makes them risky.

Why actions raise the stakes

When a model only writes text, a mistake is just wrong text you can ignore. When an agent can act — change a record, send a message, restart a service, spend money — a mistake has real-world consequences. Several factors make this harder than a single Q&A:

  • Errors compound. A wrong assumption in step 2 can derail steps 3 through 10. Small early mistakes snowball.
  • Non-determinism. The same task can play out differently each run (Module 10), making behavior harder to test and predict.
  • Prompt injection. If an agent reads web pages or documents, hidden malicious instructions in that content can try to hijack its actions (Module 10). An agent with real permissions is a juicier target.

Sensible safeguards

The good news: these are familiar IT controls applied to a new actor.

  • Least privilege. Give the agent only the specific, minimal permissions it needs — never blanket admin access.
  • Human-in-the-loop. Require explicit approval before high-impact or irreversible actions (deleting data, sending external email, spending).
  • Log everything. Record what the agent decided, which tools it called, and with what inputs, so actions are auditable.
  • Sandbox & rate-limit. Constrain where it can act and how often; test in non-production first.
  • Fail safe. Default to doing nothing when uncertain, and make it easy for a human to stop or reverse.

Rule of thumb

The more autonomy and access an agent has, the more rigorously it must be constrained, monitored, and reviewed. Capability and oversight should rise together — never grant broad action permissions just because a demo looked impressive.

Key takeaways

  • Tool use lets a model request actions (search, lookups, API calls) and use the results.
  • An agent loops — plan, act, observe, repeat — to complete multi-step tasks.
  • Actions turn mistakes into real-world consequences, and errors compound across steps.
  • Apply least privilege, human approval for risky steps, and thorough logging.
